# MPI inference, cluster-aware backends, CLI, dashboard, and pure-Rust provider implementation plan

> **For Hermes:** Use the `subagent-driven-development` skill to implement this plan task-by-task. Do not implement during the planning turn. Follow the release gates below; a collective demo or a process with an MPI label is not completion.

**Goal:** Run real distributed tensor-parallel inference from the CLI and dashboard through a version-pinned, locally maintained pure-Rust MPI-compatible provider, with one verified cluster-wide backend: Vulkan for heterogeneous clusters, or Metal/CUDA/ROCm when every selected rank qualifies for the corresponding homogeneous-cluster backend.

**Architecture:** Keep llama.cpp RPC/layer splitting as the default and add an explicit `transport=mpi` path with a single server-side cluster heuristic shared by CLI and dashboard. Replace the planned C/C++-linked MPI provider with a reviewed, version-pinned Rust provider that owns bootstrap, private data-plane transport, collectives, and rank failure propagation; llama.cpp's model/graph code remains C++ and crosses to that provider only through a constrained, tested C ABI. Select one backend for the entire fixed communicator from verified capabilities of the selected physical GPUs, use separately pinned engine flavors, and preserve the rank-zero HTTP interface. Revalidate the selected backend and provider identity at planning, launch, and rank initialization; never infer execution support from hardware labels, mix backend families within one job, or rewrite global RPC preferences.

**Tech stack:** Python/uv, FastAPI/Pydantic, Typer/Rich, Svelte 5/TypeScript/Vite, Rust/PyO3, a locally maintained fork of pure-Rust `mpi-rs` `0.1.0` (upstream source revision `99be8ac11c04f5419452428a486ae0eee1f5552e`), a narrow C ABI bridge, C++/CMake only for llama.cpp/bridge integration, pinned llama.cpp `b11026`, GGML Vulkan/Metal/CUDA/HIP (ROCm) engine flavors, and corresponding GPU drivers/toolchains.

## 1. Status, scope, and execution rules

The scope includes real MPI inference and UI/CLI integration. The updated backend requirement supersedes the earlier blanket Vulkan requirement:

> When MPI is selected, choose the backend using the cluster heuristic: heterogeneous clusters MUST use Vulkan; all-Mac clusters can use Metal; all-NVIDIA clusters can use CUDA; all-AMD clusters can use ROCm.

Every rank must verify the same selected backend. Native alternatives are permissions, not proof that a driver, model, MPI provider, or engine supports them. This is not permission to ship only MPI planning: completion requires the mixed-OS Vulkan gate and the homogeneous-backend acceptance lanes below.

### Important implementation-readiness boundary

There are two unresolved engineering gates:

1. A single, operational MPI communicator spanning the intended Windows, macOS, and Linux processes has not been demonstrated. Installing MS-MPI on Windows and Open MPI elsewhere does not establish interoperability.
2. The existing collectives are not connected to llama.cpp model loading or graph execution. A distributed, rank-local implementation of llama.cpp's tensor-split graph is required. There is no existing `start_mpi`, MPI-enabled llama-server flag, or public `llama_decode_one_layer` API to wire up.

The tests, build harness, settings, admission policy, and CLI changes below have complete implementation snippets. The engine work is a gated engineering specification, not a fabricated ready-to-apply upstream patch. After the communicator/backend gates, the implementer must expand the engine work packages into reviewed, source-accurate patches and their own 2–5-minute RED/GREEN steps before implementing them. Do not guess the missing patch or substitute a no-op backend. This boundary is a limitation of the current plan, not a claim that the full runtime is already implementation-ready.

## 3. Product contract

### Mode semantics

| Setting | RPC | MPI |
|---|---|---|
| Default | Yes; legacy settings without a mode mean RPC | Explicit opt-in |
| Compute backend | Existing per-node choice | One heuristic-selected backend shared by every rank; heterogeneous clusters require Vulkan |
| Split | Existing layer split | Actual model-aware tensor split |
| CPU behavior | Existing fallback | No silent CPU matmul/attention fallback |
| Host CPU work | Existing | Tokenization, sampling, control, and MPI host-buffer staging are permitted; they are not alternative GPU backends |
| Missing binary/device/provider | Existing behavior | Block before stopping a currently healthy run |
| Missing or incompatible worker | Existing behavior | Fail the requested job; never silently drop that worker |
| Plan | Existing estimate | No processes/install/restarts; readiness + model-specific shard manifest |
| Membership shrink | Existing RPC replan | Stop the fixed-communicator MPI job and require explicit replan/restart |

### Automatic cluster backend heuristic (authoritative policy)

Classify the **selected physical GPUs on all participating members**, including the master. Do not classify by the master's GPU alone, RPC `backend`, configured preference, marketing names, memory capacity, or clock speed. The agent must report canonical OS identifiers and hardware-vendor identifiers from probing; unknown vendor IDs stay unknown. Missing inventory is a blocker, not evidence of homogeneity.

Evaluate in this order:

| Priority / participating hardware | Preferred backend | Candidates, in order | Enforcement |
|---|---|---|---|
| Every participating host is macOS | Metal | `metal`, then `vulkan` | All-Mac takes precedence over GPU vendor, including Intel/AMD Macs; Metal still needs verification on each selected GPU. |
| Otherwise every selected GPU is NVIDIA | CUDA | `cuda`, then `vulkan` | Different NVIDIA generations, sizes, and Windows/Linux hosts do not by themselves rule out a common CUDA backend. |
| Otherwise every selected GPU is AMD | ROCm | `rocm`, then `vulkan` | ROCm is eligible only where the actual platform/GPU/toolchain/engine support it. Do not assume Windows AMD can use ROCm: the current installer supports ROCm only on Linux. |
| Mixed GPU families, or unknown vendor identity | Vulkan | `vulkan` only | Mandatory; native Metal/CUDA/ROCm must not be selected, even if the master prefers them. |

Interpretation of **heterogeneous** here: no shared family in the first three rows, not merely unequal capacities or different OS versions. Thus Windows AMD + Mac + Linux NVIDIA requires Vulkan, while Windows NVIDIA + Linux NVIDIA may use verified CUDA. An all-Mac cluster is explicitly the Metal exception even with different Mac GPU vendors. This interpretation resolves overlap between the user's rules; keep it documented and tested.

At Plan time, select the first candidate for which **every selected rank** has the required engine/device/model operations and compatible engine/provider identities. Native selection does not require Vulkan to be installed. If native verification fails but Vulkan works everywhere, select Vulkan for the whole job and expose the rejected native candidate's per-node reasons; if neither works, return `effective_backend=null`, `launchable=false`, and blockers. Never mix native and Vulkan ranks, silently omit a device/node, install a flavor automatically, or treat RPC capability as MPI proof.

The selection is run-local and automatic, not a new global preference or editable unrestricted dropdown. A changed membership, selection, binary, capability fingerprint, model, or operation profile invalidates the decision and the shard manifest. Plan and launch use the same resolver; an accepted plan whose decision changes at preflight returns a stale-plan error without replacing the current healthy run. A running fixed communicator never changes backend; request a new plan/job.

One backend family is a compatibility policy, not proof of bitwise-identical arithmetic or guaranteed speedups. Test numerical quality and performance for each supported flavor.


### New request fields

Add to the shared run settings:

- `transport: "rpc" | "mpi"`, default `"rpc"`.
- `mpi_device_ids: dict[str, list[str]] | None`, default `None`. Keys are participating member node IDs; values are backend-independent physical GPU IDs reported by the capability probe. Missing keys select all reported physical GPUs on that member, including devices with no usable engine (which block admission rather than disappearing). An explicit empty list is invalid, not "silently omit this member".

Do not add an independently editable `mpi_backend` in this iteration: selecting MPI enables automatic cluster policy, and UI/CLI display the server's decision. Do not persist an effective backend in model settings; recalculate it for the current participating device set. Physical IDs must map to each flavor's actual device handle (e.g. `Vulkan0`, `CUDA0`, `Metal0`, or a probed HIP handle); never reinterpret one backend's ordinal as another's. If a stable cross-backend identity cannot be established, report the ambiguity and block that selection.

CLI minimum:

- `kllm plan --model MODEL --transport mpi`
- `kllm run --model MODEL --transport mpi`
- `kllm status` shows requested transport, effective transport, job state, and actual rank devices.
- Add an explicit device selection option only after capability discovery exists; proposed spelling is repeated `--mpi-device NODE_ID=PHYSICAL_GPU_ID`. Validate duplicate/unknown IDs; do not parse shell snippets. No CLI-only backend override may bypass the heuristic.

API response fields:

- `transport`: requested mode.
- `runtime_transport`: `"llama.cpp-rpc"` or `"mpi"` for the intended execution path.
- `cluster_class`: `"all_macs"`, `"all_nvidia"`, `"all_amd"`, or `"heterogeneous_or_unknown"`.
- `preferred_backend`: the heuristic's first candidate; `effective_backend`: `"vulkan" | "metal" | "cuda" | "rocm" | null` (`null` if no candidate passes admission).
- `backend_reason`: human-readable classification/selection explanation, plus `backend_diagnostics: dict[str, list[str]]` naming rejected candidates and failing node/devices. These are plan facts, not changes to the general member backend.
- `launchable: bool`, `blockers: list[str]`.
- `mpi`: an explicit typed schedule/job description; keep the existing descriptive RPC annotation truthful.
- `mpi_moves_activations`: false in a preview; true in live status only after engine startup and a completed collective-backed warmup/decode.
- `plan_fingerprint`, `capability_fingerprints`, `engine_revision`, `manifest_version`.

A readiness-blocked MPI plan may return HTTP 200 with `launchable=false` so the UI can display all per-node failures. Invalid request fields return the existing HTTP 400 convention. An MPI run with unmet prerequisites returns HTTP 503 or 409 (changed/stale plan), and launches nothing.

### Initial engine surface

First validated engine target: dense `llama` architecture, text generation, one concurrent sequence, explicit context, `f16` KV, flash attention enabled, no draft model, no vision, no LoRA/hot reload, no automatic context shrinking. These are proposed initial implementation limits, not claims that other models cannot work. Unsupported architecture/options must be rejected visibly; expand support only with real tests. This restriction needs approval before treating the initial implementation as the final product scope.

Keep the schema compatible with broader RPC settings. For MPI, report unsupported explicitly set values instead of silently changing them. Defaults can be resolved per mode only when the caller did not explicitly specify the field; expose every resolved value in the plan.

```cpp
#include "kllm_mpi.hpp"
#include <mpi.h>
#include <cstdint>
#include <exception>
#include <iostream>
#include <stdexcept>
#include <vector>

static void require_all(bool ok, const char * message) {
    const int local = ok ? 0 : 1;
    int any = 0;
    MPI_Allreduce(&local, &any, 1, MPI_INT, MPI_MAX, MPI_COMM_WORLD);
    if (any) {
        throw std::runtime_error(message);
    }
}

static const char * platform_name() {
#if defined(__CYGWIN__)
    return "windows-cygwin";
#elif defined(_WIN32)
    return "windows-native";
#elif defined(__APPLE__)
    return "macos";
#elif defined(__linux__)
    return "linux";
#else
    return "other";
#endif
}

int main(int argc, char ** argv) {
    int provided = 0;
    if (MPI_Init_thread(&argc, &argv, MPI_THREAD_SERIALIZED, &provided) != MPI_SUCCESS) {
        return 2;
    }
    int rank = 0;
    int size = 0;
    MPI_Comm_rank(MPI_COMM_WORLD, &rank);
    MPI_Comm_size(MPI_COMM_WORLD, &size);
    try {
        require_all(provided >= MPI_THREAD_SERIALIZED, "MPI thread support insufficient");
        require_all(size >= 2, "this test needs at least two ranks");

        char hostname[MPI_MAX_PROCESSOR_NAME] = {};
        int hostname_len = 0;
        MPI_Get_processor_name(hostname, &hostname_len);
        std::cout << "rank=" << rank << " world=" << size
                  << " platform=" << platform_name()
                  << " host=" << std::string(hostname, hostname_len) << std::endl;

        const std::int64_t three[4] = {3, 1, 1, 1};
        auto broadcast = kllm_mpi::Tensor::f32({1.0f, 2.0f, 3.0f}, three, 0, 0, false);
        if (rank != 0) {
            broadcast.data.clear();
        }
        kllm_mpi::mpi_balanced_bcast(broadcast, 0);
        require_all(broadcast.f32_values() == std::vector<float>({1, 2, 3}), "broadcast mismatch");

        auto sum = kllm_mpi::Tensor::f32(
            std::vector<float>(3, static_cast<float>(rank + 1)), three, rank, 1, true);
        kllm_mpi::mpi_balanced_allreduce(sum, "row_sum", nullptr);
        const float expected = static_cast<float>(size * (size + 1) / 2);
        require_all(sum.f32_values() == std::vector<float>(3, expected), "allreduce mismatch");

        const std::int64_t width[4] = {rank + 1, 1, 1, 1};
        auto shard = kllm_mpi::Tensor::f32(
            std::vector<float>(rank + 1, static_cast<float>(rank)), width, rank, 2, true);
        kllm_mpi::mpi_balanced_allreduce(shard, "column_concat", nullptr);
        std::vector<float> concatenated;
        for (int r = 0; r < size; ++r) {
            concatenated.insert(concatenated.end(), r + 1, static_cast<float>(r));
        }
        require_all(shard.f32_values() == concatenated, "allgatherv mismatch");

        auto invalid = kllm_mpi::Tensor::f32({1, 2, 3}, three, 0, 3, false);
        if (rank == 0) {
            invalid.flags = 0x8000;
        }
        bool rejected = false;
        try {
            kllm_mpi::mpi_balanced_bcast(invalid, 0);
        } catch (const std::exception &) {
            rejected = true;
        }
        require_all(rejected, "invalid header was not rejected on every rank");
        if (rank == 0) {
            std::cout << "kllm_mpi real collectives ok world=" << size << std::endl;
        }
        MPI_Finalize();
        return 0;
    } catch (const std::exception & error) {
        std::cerr << "rank=" << rank << " error=" << error.what() << std::endl;
        MPI_Abort(MPI_COMM_WORLD, 1);
        return 1;
    }
}
```

```python
"""Cluster-wide MPI backend policy; independent of RPC preferences."""
from __future__ import annotations
from collections.abc import Sequence
from typing import Any


class MpiAdmissionError(ValueError):
    pass


def _backend_candidates(selected):
    if all(cap["platform"] == "darwin" for _, cap, _ in selected):
        return "all_macs", ("metal", "vulkan"), "All participating hosts are macOS"
    vendors = {device.get("vendor", "unknown") for _, _, device in selected}
    if vendors == {"nvidia"}:
        return "all_nvidia", ("cuda", "vulkan"), "All selected GPUs are NVIDIA"
    if vendors == {"amd"}:
        return "all_amd", ("rocm", "vulkan"), "All selected GPUs are AMD"
    return "heterogeneous_or_unknown", ("vulkan",), "Mixed or unknown GPU families require Vulkan"


def _ranks_for_backend(selected, backend):
    ranks, errors = [], []
    identity = None
    for node_id, cap, physical in selected:
        physical_id = physical["physical_id"]
        label = f"{node_id}/{physical_id}"
        report = cap.get("backends", {}).get(backend, {})
        if report.get("available") is not True or report.get("backend") != backend:
            errors.append(f"{label}: {backend} unavailable: {report.get('reason', 'no verified flavor')}")
            continue
        engine, provider, fingerprint = (report.get(key) for key in
            ("engine_revision", "mpi_compatibility_id", "fingerprint"))
        if not all(isinstance(v, str) and v for v in (engine, provider, fingerprint)):
            errors.append(f"{label}: incomplete {backend} engine/provider identity")
            continue
        current = (engine, provider)
        if identity is None:
            identity = current
        elif current != identity:
            errors.append(f"{label}: incompatible {backend} engine/provider")
            continue
        devices = report.get("devices") or []
        ids = [device.get("physical_id") for device in devices]
        handles = [device.get("device") for device in devices]
        if (not all(isinstance(v, str) and v for v in ids + handles)
                or len(set(ids)) != len(ids) or len(set(handles)) != len(handles)):
            errors.append(f"{label}: ambiguous {backend} physical/device inventory")
            continue
        matches = [device for device in devices if device["physical_id"] == physical_id]
        if len(matches) != 1 or matches[0].get("backend") != backend:
            errors.append(f"{label}: no verified {backend} device mapping")
            continue
        ranks.append({
            **matches[0], "rank": len(ranks), "node_id": node_id, "backend": backend,
            "capability_fingerprint": cap["fingerprint"], "engine_fingerprint": fingerprint,
            "engine_revision": engine, "mpi_compatibility_id": provider,
        })
    return ranks, errors


def select_mpi_ranks(
    members: Sequence[dict[str, Any]],
    selection: dict[str, list[str]] | None = None,
) -> dict[str, Any]:
    requested = selection or {}
    ids = [member.get("node_id") for member in members]
    if (not ids or not all(isinstance(v, str) and v for v in ids)
            or len(set(ids)) != len(ids)):
        raise MpiAdmissionError("MPI requires unique nonempty node IDs")
    if sum(member.get("role") == "master" for member in members) != 1:
        raise MpiAdmissionError("MPI requires exactly one master")
    if set(requested) - set(ids):
        raise MpiAdmissionError(f"unknown MPI members: {sorted(set(requested) - set(ids))}")
    ordered = sorted(members, key=lambda member: (member.get("role") != "master", member["node_id"]))
    selected = []
    for member in ordered:
        node_id = member["node_id"]
        cap = member.get("mpi_capabilities") or {}
        if (cap.get("protocol") != 1 or cap.get("available") is not True
                or cap.get("platform") not in {"darwin", "win32", "linux"}
                or not isinstance(cap.get("fingerprint"), str) or not cap["fingerprint"]):
            raise MpiAdmissionError(f"{node_id}: MPI capability inventory unavailable or incomplete")
        devices = cap.get("devices") or []
        physical_ids = [device.get("physical_id") for device in devices]
        if (not physical_ids or not all(isinstance(v, str) and v for v in physical_ids)
                or len(set(physical_ids)) != len(physical_ids)):
            raise MpiAdmissionError(f"{node_id}: invalid or duplicate physical inventory")
        by_id = {device["physical_id"]: device for device in devices}
        wanted = requested.get(node_id, list(by_id))
        if (not wanted or len(set(wanted)) != len(wanted) or set(wanted) - set(by_id)):
            raise MpiAdmissionError(f"{node_id}: MPI requires nonempty unique known physical IDs")
        selected.extend((node_id, cap, by_id[physical_id]) for physical_id in sorted(wanted))
    cluster_class, candidates, reason = _backend_candidates(selected)
    result = {
        "cluster_class": cluster_class, "preferred_backend": candidates[0],
        "effective_backend": None, "backend_reason": reason,
        "backend_diagnostics": {}, "ranks": [], "blockers": [],
    }
    for backend in candidates:
        ranks, errors = _ranks_for_backend(selected, backend)
        if errors:
            result["backend_diagnostics"][backend] = errors
            continue
        result["effective_backend"] = backend
        result["ranks"] = ranks
        if backend != candidates[0]:
            reason += f"; {candidates[0]} unavailable for this job; using verified common Vulkan"
        result["backend_reason"] = reason
        return result
    result["blockers"] = [error for errors in result["backend_diagnostics"].values() for error in errors]
    return result
```

#### Required execution design

- Every rank has the same logical model/graph/shard manifest and the local model file, but allocates and executes only the shards belonging to its assigned physical GPU using the single selected job backend.
- Rank zero is on the cluster master. One rank per selected physical GPU, ordered deterministically (master first, then stable node/physical-ID order). Resolve that physical ID to the chosen flavor's verified handle. No duplicate native+Vulkan identity for one physical GPU, and no mixed backend families in a communicator.
- Reuse llama.cpp's model-aware tensor split logic instead of assigning `n_cols=embedding_length` uniformly to every model tensor.
- Rank-local allocations must cover real Q/K/V/GQA/MQA and FFN shapes, quantization block alignment, output/embedding tensors, and KV layout. The exact same shard manifest must drive plan estimates, weight loading, graph views, and actual execution.
- Initially use host-staged dense f32 collective buffers: synchronize the chosen GGML GPU backend's producer, read contiguous activation data, collective, upload through that same backend, then continue the consumer graph. Use backend-neutral GGML synchronization/buffer APIs, not Vulkan-specific staging assumptions; validate Metal/CUDA/HIP streams and ownership separately. Do not pass GPU pointers directly to a generic MPI library.
- Unequal weight shard widths can produce equal-shaped output partial sums. Use `MPI_Allreduce` for the equal-shaped partial result, not `Allgatherv` merely because weights are uneven. Use `Allgatherv` only when concatenation is the correct tensor operation.
- Each participating rank must enter collectives in the same order. Add operation sequence, phase, layer, shape, dtype and manifest agreement before transferring data. Do not rely on a sender's `activation` flag to prove a buffer is not a weight: validate the buffer's engine provenance.
- Do not send weight or KV buffers through the activation bridge. Model distribution is a separate pre-run operation and may transfer model files.
- Rank zero owns tokenization, sampling, HTTP and streaming. It broadcasts decode batches and every supported KV-state operation. Other ranks do not bind the HTTP inference port.
- Preserve server cancellation, end-of-sequence, next-request reset, stop, and rank failure semantics. A rank-local exception must either be agreed before the next collective or cause whole-job termination with a bounded watchdog; no survivor hangs indefinitely.
- Warmup must execute the actual distributed graph before the job is marked ready.

## 8. Risks, tradeoffs, and open decisions

1. **Cross-OS MPI distribution is a hard gate.** A shared API/ABI or standard version does not establish process-manager/wire interoperability. Cygwin/Open MPI is an investigation candidate, not verified native Windows support. If only a compatibility-layer solution passes, get approval and label it precisely.
2. **This is an engine project, not merely plumbing.** The upstream meta backend assumes local device ownership in many allocation and execution paths. A callback-only patch will not create distributed TP. Budget a proper native review and model correctness work.
3. **Model support needs a bounded first target.** Dense llama/text-only/single-sequence is proposed to make correctness achievable. The user has not approved excluding other model families as the final scope. Do not silently label a restricted demo as universal support.
4. **All backend availability is per binary, platform, driver, operation, and model.** Metal discovery does not prove Vulkan on a mixed-cluster Mac; likewise NVIDIA/AMD labels do not prove CUDA/ROCm MPI execution. The current installer supports ROCm only on Linux. Treat missing native support as a diagnosed planning-time Vulkan candidate, not permission to mislabel or mix ranks. A working device enumeration alone is insufficient for every backend.
5. **Precision is not guaranteed by the backend label.** Different GPU vendors/drivers and reduction orders can differ numerically. Quantization alignment, f32 reduction staging, deterministic comparison prompts, and agreed tolerances are required.
6. **Memory estimates must match real shard layout.** Existing generic MPI column caps reserve full KV per rank; upstream tensor mode may shard KV. Pick the implemented layout and account for it exactly, including scratch and host staging. Do not reuse the wrong estimator because it returns a number.
7. **Network traffic can erase TP gains.** Host-staged MPI plus per-layer reductions may be slower than RPC layer splits on ordinary LAN/Wi-Fi. Correctness and truthful measurements precede performance claims.
8. **Security/lifecycle scope is larger than a launcher PID.** Provider daemons, workers, private ports, authenticated launch endpoints, startup timeouts, recovery and job-tree cleanup must be verified. Do not reuse the current master-only key check for worker process launch.
9. **Installer isolation matters.** An MPI flavor must not overwrite another flavor or a user's working RPC installation, or reuse an incompatible cached pack. A successful native-only cluster must not be blocked by a missing Vulkan flavor.
10. **Plan completeness boundary.** Gates A/B and the engine-patch addendum are prerequisites to an implementation-ready full runtime plan. The current document intentionally does not invent their successful output, missing C++ patch, exact provider deployment commands, or hardware test results.

## 10. Authoritative pure-Rust provider amendment

### 10.1 Decision and boundary

The runtime provider is now a locally maintained fork of `mpi-rs` `0.1.0`, derived from upstream source revision `99be8ac11c04f5419452428a486ae0eee1f5552e`. It is an MPI-compatible Rust runtime over TCP; it is not an `rsmpi` binding to Open MPI, MPICH, or MS-MPI. This intentionally replaces the earlier requirement for a common native MPI implementation.

The change removes the native MPI library/toolchain dependency, but it does **not** remove any correctness, cross-platform, security, lifecycle, backend, or real-GPU acceptance gate. The provider is not admitted merely because its API uses MPI names or because a local smoke succeeds.

The evaluation that triggered this amendment must remain visible:

- The upstream `mpi-rs` release completed a local three-rank Windows broadcast/all-reduce/all-gather smoke.
- Its full upstream `cargo test` currently fails on this host: its `derive` integration build uses an incompatible `mpi-derive` API, causing all 18 integration tests to fail after the first setup failure.
- An unannounced rank exit left the upstream launcher waiting until an external bounded supervisor force-killed its owned process tree.

Therefore, do not consume the crates.io release unchanged and do not expose its bundled SSH launcher in production. The local fork must pass the replacement gate below before it can carry a planned or live KLLM job.

The earlier ban on a homemade socket protocol is superseded only for this reviewed, version-pinned provider. No KLLM client, worker, or engine patch may invent a second ad-hoc transport or bypass its authenticated provider protocol.

### 10.2 Provider source and test layout

Keep the package lockfile, upstream revision, local patch digest, protocol version, and cargo/rustc target in a machine-readable provider stamp. Use a local path dependency for the matching upstream `mpi-derive` source; do not resolve a similarly named incompatible registry macro.

The provider package owns these targets:

- `kllm-mpi-rank`: a rank process with no user-supplied shell command or executable path.
- `kllm-mpi-provider-check`: bounded local provider self-test and capabilities JSON; it is not an inference server.
- A C ABI library for the llama.cpp bridge. C ABI functions return status/error buffers; Rust panics must never unwind into C++.

Create provider-focused tests before implementation:

1. `cargo test --manifest-path crates/kllm-mpi-provider/Cargo.toml --all-targets --features derive` must first reproduce the upstream failure, then pass after the local `mpi-derive` correction.
2. `tests/provider_local.rs` must launch exactly three local ranks and verify broadcast, equal-shaped all-reduce, unequal-width all-gatherv, bad-header agreement, normal finalization, and deterministic rank order.
3. `tests/provider_failure.rs` must terminate—not panic—one rank during a blocked collective. Within the configured bound, the supervisor must reap every owned rank and launcher process, report the failed rank, and leave no matching process alive.
4. `tests/provider_security.rs` must reject a wrong job/rank/protocol identity, replayed nonce, unexpected peer address, bad authentication tag, host/argv/environment injection, and an out-of-range data-plane port before any payload collective.
5. `tests/provider_interop.rs` is a three-host fixture run only when all actual Windows/macOS/Linux hosts are configured. It exercises the same collective set and forced-rank-loss cleanup through the production control-plane launch path.

Do not enable the optional POSIX shared-memory feature for the Windows-compatible baseline. It can become a separately tested optimization only after the TCP provider meets every release gate.

### 10.3 Production launch and data-plane security

The bundled upstream `mpiexec --host`/`--remote-bin` SSH path is test-only and must not be used by `kllm`. In particular, no code may concatenate a remote shell command from client data.

Production launch uses the authenticated KLLM control plane:

1. The master creates a structured, server-owned `MpiJobSpec` from the accepted plan. It contains only resolved rank identity, approved local model identifier, selected physical ID/backend handle, fixed private bind interface/port allocation, provider revision/protocol, and manifest identity.
2. The master prepares each worker through authenticated, constant-time-checked worker endpoints. Clients cannot submit executable paths, host strings, raw `mpiexec` arguments, an environment dictionary, a port, or a shell fragment.
3. Each node starts its owned `kllm-mpi-rank` from the structured spec. Secrets are delivered through protected local/control-plane channels, never command-line arguments, logs, status JSON, host files, or persisted plan snapshots.
4. The data plane binds only to an approved private interface and an explicitly allocated configured port range; it never auto-selects `0.0.0.0`, uses a public route probe, or opens an arbitrary listener.
5. Before accepting collective traffic, peers mutually authenticate the provider protocol with a per-job secret, provider revision, job ID, rank/world identity, address binding, and fresh nonce. A peer mismatch/replay immediately fails the whole pre-ready job.
6. The master and every worker own their rank process tree. On Windows use a Job Object or an equivalent verified containment mechanism; on Unix use a process group or equivalent. An unannounced rank loss, timeout, or control-plane cancellation must terminate and reap the entire owned job, not merely the local launcher PID.

Provider identity is part of every capability, plan fingerprint, rank report, and status response: upstream revision, local fork patch digest, protocol version, binary hash, target triple, and selected feature set. Any change requires a new plan.

### 10.4 Rust/C++ boundary and engine requirements

The provider replaces direct `mpi.h` calls, not llama.cpp's graph implementation. The rank-local tensor-parallel engine remains a reviewed patch against pinned llama.cpp `b11026` and retains all original model-aware shard, backend, and warmup requirements.

Replace `KLLM_HAVE_MPI` use in the live bridge with a narrow C ABI such as provider initialization/finalization, rank/world query, authenticated broadcast, f32 all-reduce, byte all-gatherv, abort, and health/sequence agreement. Define ownership, byte length, dtype, timeout, and error semantics in a C header and test them from both Rust and C++. Never pass GPU pointers to Rust TCP transport; synchronize and host-stage through backend-neutral GGML APIs before collective calls, then upload through the same selected backend.

The existing C++ activation implementation may remain as protocol/reference tests, but it is not a production provider. Remove the unverified native-MPI CMake smoke branch (`cpp/kllm_mpi/CMakeLists.txt` and `cpp/kllm_mpi/mpi_smoke_test.cpp`) created before this amendment; the Rust provider tests above replace it.

### 10.5 Revised ordered gates

## 11. Revised definition of done

All original backend, graph, model, UI, CLI, lifecycle, and RPC-regression criteria remain required. In addition, the pure-Rust provider is complete only when all of the following are true:

- [ ] The locally maintained provider source, license notices, upstream revision, local patch digest, protocol version, target triple, binary hash, and feature set are pinned and surfaced in capability/plan/status evidence.
- [ ] The full provider unit/integration suite, including the repaired `derive` target, passes on every supported target; the original failing release is never used unpatched.
- [ ] Production launch has no client-controlled remote shell, executable path, hostfile, raw environment, raw port, or raw `mpiexec` argument path.
- [ ] Each job uses authenticated peer handshakes, fixed private interfaces/allocated port ranges, and secrets absent from argv, logs, plans, and status.
- [ ] An externally terminated rank causes bounded whole-job cleanup with no owned process left alive and no unrelated process killed, on Windows, macOS, and Linux.
- [ ] One authenticated provider world spans Windows AMD, macOS, and Linux NVIDIA before it is described as cross-platform; a local smoke or macOS/Linux-only run is not sufficient.
- [ ] The Rust/C++ ABI is tested for lifecycle, sequence agreement, error handling, host staging, and no Rust panic crossing the boundary.
- [ ] Actual llama.cpp tensor-parallel graph execution, selected backend proof, CLI/dashboard behavior, model-aware manifests, and all heterogeneous/homogeneous acceptance lanes satisfy the original Definition of Done.

Only then describe the pure-Rust MPI/UI/CLI integration as complete.
